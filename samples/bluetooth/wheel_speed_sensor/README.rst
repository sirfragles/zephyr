.. zephyr:code-sample:: wheel_speed_sensor
   :name: LIS2DH12 wheel speed sensor with BLE DFU
   :relevant-api: sensor_interface bt_gatt mcumgr

   Detect wheel revolutions with the LIS2DH12 FIFO, expose the Bluetooth CSC service,
   and update the application over BLE using MCUboot and MCUmgr.

Overview
********

This prototype targets ``holyiot_25008/nrf54l15/cpuapp``. The module is mounted on
the rotating hub with its PCB parallel to the wheel. LIS2DH12 FIFO samples are decoded
into a wheel revolution counter and the standard Bluetooth Cycling Speed and Cadence
service publishes cumulative wheel revolutions and the last wheel event time.

The application also exposes the MCUmgr SMP service. The initial image, including
MCUboot, must be programmed once with an SWD probe. Subsequent signed application
images can be uploaded over Bluetooth with nRF Connect Device Manager.

This is a hardware-validation sketch. Axis selection, vibration rejection, battery
measurement, and power tuning must be calibrated with measurements from the physical
module before using it as a finished product.

Building the initial image
**************************

Build the application and MCUboot together using sysbuild:

.. code-block:: console

   west build -b holyiot_25008/nrf54l15/cpuapp --sysbuild \
     samples/bluetooth/wheel_speed_sensor -d build-wheel

Program the sysbuild-generated merged HEX file once through SWD. Keep SWDIO, SWCLK,
VDD, and GND test pads available as an emergency recovery path even if a permanent
connector is not fitted.

Updating over Bluetooth
***********************

#. Install ``nRF Connect Device Manager`` on iOS or Android.
#. Connect to ``Open Wheel Speed``.
#. Select the image management function and upload the signed application binary
   generated by the sysbuild application image.
#. Mark the uploaded image for test and reset the device.
#. The application confirms the image after the LIS2DH12 FIFO and decoder produce a
   valid buffer. MCUboot reverts the update on the next reset if this health check fails.

Increment the application version in ``VERSION`` for every released update. The BLE
upload file is ``build-wheel/wheel_speed_sensor/zephyr/zephyr.signed.bin``; never upload
the unsigned ``zephyr.bin`` file.

Development keys
****************

The default MCUboot key distributed with the source tree is suitable only for local
development. Before distributing hardware, generate a private signing key, keep it
outside the repository, configure ``SB_CONFIG_BOOT_SIGNATURE_KEY_FILE``, and rebuild
MCUboot during provisioning. Losing that private key prevents future signed updates.

Recovery limitations
********************

BLE upload is handled by the running Zephyr application, while MCUboot validates and
installs the image. Dual-slot rollback protects against most faulty updates, but it
cannot recover from physical flash corruption or an incorrectly provisioned bootloader.
SWD pads remain the final recovery mechanism.
